# Архитектура приложения

## 1. Трёхслойная архитектура

В основе приложения лежит трёхслойная архитектура:

- слой представления;
- слой логики;
- слой данных.

Store и Bridge не являются отдельными доменными слоями: это механизмы связи.
Store — контейнер UI-состояния, Bridge — переходник между логикой и store.

### 1.1. Слой представления (UI)

Слой представления выводит пользователю данные, читает store и отправляет команды через `GameManager`/`GameLoop`. UI не вызывает внутренние сервисы логики напрямую и не пишет в store. Основной бизнес-логики здесь нет, но есть простейшая UI-валидация: активна ли кнопка, корректен ли формат ввода, нужно ли показать подсказку.

### 1.2. Слой логики

Слой логики содержит основную бизнес-логику и все вычисления. Во время работы он хранит текущее игровое состояние в памяти: ресурсы, здания, население и т.д. Долговременное хранение этого состояния — задача слоя данных; логика обращается к нему при инициализации, сохранении и загрузке, а не на каждом тике.

### 1.3. Слой данных

Слой данных хранит долговременные данные приложения. В нём есть две разные категории:

- **Контент игры** — статические описания того, что существует в игре: ресурсы, здания, население, генераторы. Разработчик задаёт их в `src/data/*.json`; во время работы они не меняются. Логика читает их при инициализации и создаёт по ним runtime-экземпляры.
- **Состояние игрока** — сохранения конкретной игры: текущие количества ресурсов, построенные здания, население и т.д. Оно создаётся логикой во время игры, меняется и сохраняется через `SaveManager`; сейчас в `localStorage`, позже — в Yandex cloud через адаптер.

Важно различать описание и экземпляр. В `buildings.json` лежит описание типа здания, а не конкретное здание с `owned`, `hp` и `decay`. Конкретный `Building` создаётся в логике из этого описания. Аналогично `resource.json` описывает тип ресурса, а текущее количество живёт в runtime-состоянии и сохраняется отдельно.

Новые типы зданий и ресурсов можно добавлять через контент, если их поведение укладывается в общую схему. Если у объекта уникальная механика, одного JSON недостаточно — понадобится отдельная логика.

Слой данных сам не интерпретирует данные и не содержит бизнес-логики. Формат контента задаётся схемой JSON и типами вроде `ResourceData`/`BuildingData`; формат сохранения — контрактом `Saveable` и методами `serializeForSave`/`deserializeForSave`. Слой данных только хранит и отдаёт данные.

### 1.4. Границы и зависимости

Слои не знают о внутреннем устройстве друг друга, но зависят от публичных контрактов. Зависимости направлены сверху вниз: представление зависит от store и публичных команд логики, логика — от EventBus, shared-контрактов и данных, данные не зависят от логики и представления.

## 2. Как слои общаются

### Presentation → Logic

- UI читает store через селекторы.
- UI отправляет команды только через публичный фасад: `GameManager.send(...)` или `GameLoop.start/setSpeed`.
- UI не импортирует внутренние классы логики и не читает состояние логики напрямую.
- Инициализация bridge и запуск цикла — задача composition root (например, `page.tsx` или отдельного провайдера), а не бизнес-команда UI.

### Logic → Presentation

- Logic не импортирует store и UI.
- Logic сообщает об изменениях через `EventBus`.
- `Bridge` подписан на события, вызывает `serialize()`/`serializeEconomy()` и пишет в store.
- `setState` вызывается только в `src/integration/storeBridge.ts`.

Направление одностороннее: Logic → EventBus → Bridge → Store. Обратные команды UI → Logic идут через `GameManager`/`GameLoop`, а не через bridge.

### Logic ↔ Data

- Статические определения (`src/data/*.json`) читаются при инициализации и дальше не меняются.
- Сохранения: `SaveManager` вызывает `serializeForSave()`/`deserializeForSave()`.
- Сейчас хранилище — `localStorage`; позже — Yandex cloud через адаптер.
- Logic не работает с файлами и сетью напрямую: только через `SaveManager` или адаптер.
- Слой данных пассивен: он хранит и отдаёт данные, но не содержит бизнес-логики.

## 3. Поток обновления UI

Схема ниже показывает не иерархию слоёв, а поток данных:

```text
UI ──читает──> Store
UI ──команды──> GameManager / GameLoop
GameManager / GameLoop ──события──> EventBus
EventBus ──уведомляет──> Bridge
Bridge ──setState──> Store
```

Store и Bridge — не отдельные доменные слои, а механизмы связи. Store хранит UI-состояние, Bridge — единственное место встречи store и logic.

## 4. Слои подробнее

### 4.1. Слой представления

Слой использует React, Tailwind CSS и остальной UI-стек. Основной файл — `page.tsx`, который собирает страницу из более мелких компонентов и инициализирует bridge и игровой цикл.

### 4.2. Слой логики

В основе лежит `GameLoop`, который задаёт ритм игры и через `GameManager` инициирует тик. `GameManager` — оркестратор слоя логики: он содержит `EventBus` и системы (например, `EconomySystem`, `SaveManager`), а также связывает их при инициализации.

Правило общения:

- **Внутри одной системы** модули могут вызывать друг друга напрямую, если это следует из их логики. Например, `BuildingManager` и `PopulationSystem` могут обращаться к `ResourceManager`, потому что все они входят в `EconomySystem`: здания и население производят и потребляют ресурсы, и это естественная внутренняя связь.
- **Между разными системами** прямых вызовов быть не должно. `EconomySystem`, `ResearchSystem`, `SaveManager` и другие системы общаются только через `EventBus`: подписываются на события и эмитят их.
- `GameManager` связывает системы при инициализации, но не заменяет `EventBus` для их бизнес-взаимодействия.
- `SaveManager` не вызывает бизнес-методы систем. Его взаимодействие ограничено контрактом `Saveable`: `serializeForSave`/`deserializeForSave` у зарегистрированных модулей.

`EventBus` остаётся единственным каналом межсистемного общения и точкой, на которую подписывается bridge. Внутри системы прямой вызов допустим и не является нарушением архитектуры.

### 4.3. Слой данных

Статическая часть слоя данных сейчас представлена папкой `src/data` с JSON-файлами:

- `resource.json` — описания ресурсов;
- `buildings.json` — описания зданий;
- `population.json` — описания населения.

Каждый файл содержит описания объектов конкретного типа. Логика читает их при инициализации и создаёт runtime-экземпляры. Сохранения игрока — отдельная часть слоя данных; они не лежат в `src/data` и обслуживаются `SaveManager`/адаптером хранилища.
