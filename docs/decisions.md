# Журнал решений

## 2026-11-25. Transient-ресурсы и BuildPower как поток

**Контекст:** по дизайну `BuildPower` — поток, а не запас: производится и
расходуется в одном ходу, остаток исчезает, в сейв не попадает. Раньше
обнуление получалось как побочный эффект `spoilRate = 1`, а `serializeForSave`
сохранял `BuildPower` как обычный ресурс.

**Решение:**

- transient-ресурсы задаются в логике набором `TRANSIENT_RESOURCE_IDS`
  (`BuildPower`): контент v1 не содержит поля `transient`, а `src/data/*.json`
  в этой задаче не меняются;
- `ResourceManager.tick()` сбрасывает transient-ресурсы после порчи и до записи
  истории баланса;
- transient-ресурсы не участвуют в порче излишков;
- `serializeForSave()` исключает transient из ресурсов и истории,
  `deserializeForSave()` игнорирует их и обнуляет состояние потока после
  загрузки;
- `serializeForStore()` оставляет transient, чтобы UI видел поток текущего хода;
- отсутствие обратной связи внутри фазы производства обеспечивается снимком
  `available` в `processRequests` и не требует отдельного механизма.

**Следствия:** при добавлении нового потока достаточно расширить
`TRANSIENT_RESOURCE_IDS`; при появлении поля `transient` в контенте набор можно
заменить на чтение признака из данных. Существующий тест порчи с `BuildPower`
остаётся зелёным, но после этапа 1.2 проверяет сброс потока, а не порчу; его
уточнение — отдельная задача.

## 2026-11-25. Переход на TDD

**Контекст:** тесты писались после реализации, поэтому могли подстраиваться
под текущий код, а не под дизайн. Нужен явный порядок, не зависящий от того,
кто и когда пишет реализацию.

**Решение:**

- для новой механики, нового поведения или изменения контракта сначала
  пишутся тесты по дизайну;
- тесты проходят красную стадию: падают именно из-за отсутствия логики,
  причина падения фиксируется в отчёте о задаче;
- после красной стадии тестовый файл и связанные фикстуры/хелперы из
  `src/test/` замораживаются и не меняются без явного разрешения пользователя;
- реализация пишется до зелёного прогона; подгонять тест под код запрещено;
- заморозка сохраняется и после зелёного прогона;
- TDD применяется только к разработке вперёд: уже реализованные модули не
  переписываются под TDD;
- `test.fails` остаётся для известных багов уже реализованного кода и не
  заменяет красную стадию.

**Следствия:** порядок закреплён в [`AGENTS.md`](../AGENTS.md) (раздел TDD),
[`docs/testing.md`](testing.md) §2–3 и [`docs/architecture.md`](architecture.md)
§5.1; порядок внедрения новых механик — в
[`plans/testing-strategy.md`](../plans/testing-strategy.md) §1.2.

## 2026-11-25. Парадигма тестирования вынесена в docs

**Контекст:** принципы, уровни и организация тестов жили только в
`plans/testing-strategy.md`, а `docs` фиксировал лишь счётчики в `status.md`.
Планы меняются от этапа к этапу, парадигма должна быть стабильной и
обнаружимой рядом с архитектурой.

**Решение:**

- создать `docs/testing.md` как источник истины для парадигмы и текущего
  состояния тестов;
- оставить `plans/testing-strategy.md` планом и порядком внедрения;
- закрепить тестовые границы слоёв в `docs/architecture.md`, §5;
- факты покрытия и известные баги хранить в `docs/status.md`.

**Следствия:** новые тестовые практики и инварианты фиксируются в
`docs/testing.md`; изменения порядка покрытия — в `plans/testing-strategy.md`;
факты по шагам — в `docs/status.md`.

## 2026-11-24. Взаимодействие менеджеров и EventBus

**Контекст:** нужно однозначно разделить внутрисистемные и межсистемные
вызовы, чтобы `BuildingManager` мог получать ресурсы у `ResourceManager`
без EventBus, но системы оставались развязанными.

**Решение:**

- между системами (`EconomySystem`, `SaveManager`, будущие `ResearchSystem`
  и т.д.) — только EventBus;
- внутри одной системы менеджеры вызывают публичные методы друг друга
  напрямую, если это следует из логики;
- `BuildingManager` → `ResourceManager`: формирует `ResourceRequest[]`,
  вызывает `processRequests`, затем `applyRequests`;
- запросы одной фазы собираются в один батч, иначе приоритеты и дефицит
  распределятся неверно;
- ресурсы мутирует только `ResourceManager`; другие менеджеры не трогают
  `Resource` напрямую;
- строительство использует отдельное распределение `BuildPower`, а не общий
  `ResourceRequest`;
- обратные зависимости запрещены: `ResourceManager` не знает о зданиях;
  при необходимости уведомления — EventBus.

**Причина:** прямой вызов нужен там, где есть результат (`satisfactionCoeff`,
`actualConsumes`, `actualProduces`) и фиксированный порядок фаз; EventBus
не возвращает значения и не задаёт порядок.

**Следствия:** `EconomySystem` оркестрирует порядок фаз, менеджеры не
подписываются на `tick` самостоятельно. Детали — `docs/architecture.md` §4.2.

## 2026-11-24. Тестовый раннер и организация тестов

**Контекст:** нужен unit-раннер для логики без привязки к Next.js и UI.

**Решение:**

- раннер — Vitest 4.1.12; окружение по умолчанию `node`, jsdom включается
  docblock-ом `// @vitest-environment jsdom` только для `GameManager` и `GameLoop`;
- `globals: true`; импорт `describe/it/expect/vi` из `vitest` в текущей
  CJS-конфигурации проекта терял контекст suite, глобалы работают стабильно;
- alias `@/*` — нативное `resolve.tsconfigPaths` Vite 8, без
  `vite-tsconfig-paths`;
- тесты лежат рядом с кодом (`src/logic/**/*.test.ts`), общая инфраструктура —
  в `src/test/` (setup, helpers, fixtures);
- известные баги фиксируются `test.fails` со ссылкой на `docs/status.md`,
  а не ослаблением проверок;
- Vitest 5.1.1 не используется: в этой конфигурации терял контекст suite.

**Следствия:** `npm run test`, `npm run test:watch`, `npm run test:coverage`;
coverage включает `src/logic/**` и `src/integration/**`, легаси-модули
`Generator`, `BuildingSystem`, `PopulationSystem` исключены до своей реализации.
