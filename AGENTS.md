# AGENTS.md

## Project

Браузерная экономическая idle-игра: Next.js + React + TypeScript + Zustand.
Главная ценность — **слоистая архитектура**: логика не зависит от UI,
модули логики общаются через EventBus.

## Архитектура

Зависимости идут сверху вниз:

```text
UI (React components, hooks)
  ↓ читает Store, отправляет команды в GameManager / GameLoop
Store (Zustand) — контейнер UI-состояния
  ↓ пишется только из bridge
Bridge (src/integration/) — единственное место встречи store и logic
  ↓ подписан на EventBus
Logic (GameLoop, GameManager, сервисы) — знает только EventBus, shared-типы и JSON
```

Store и bridge — не доменные слои, а механизмы связи. Подробности —
[`docs/architecture.md`](docs/architecture.md).

Ключевые модули:

- **EventBus** (`src/logic/EventBus.ts`) — `on/off/emit`, единственный канал
  межсистемного общения.
- **GameManager** (`src/logic/GameManager.ts`) — оркестратор и фасад команд
  (`send(event, payload)`), содержит системы.
- **GameLoop** (`src/logic/GameLoop.ts`) — тик, скорость, fast-forward.
- **EconomySystem** (`src/logic/services/Economy/`) — модуль экономики,
  подписан на `"tick"`; внутри `ResourceSystem`, позже `BuildingSystem`
  и `PopulationSystem`.
- **SaveManager** (`src/logic/services/GameSave/`) — сохранения через EventBus.
- **store** (`src/store/gameStore.ts`) — Zustand, только данные для UI.
- **bridge** (`src/integration/storeBridge.ts`) — EventBus → `serialize()` → store.

### Инварианты

- `src/logic/**` не импортирует `@/store/*`, `GameState` и UI.
- `useGameStore.setState` вызывается только в `src/integration/storeBridge.ts`.
- `GameLoop` и `GameManager` создаются только через `getGameLoop()` /
  `getGameManager()`. Синглтоны живут на `globalThis`, не в скоупе модуля;
  `new` на top-level и вне аксессоров запрещён.
- `GameLoop.start()` идемпотентен, начинается с
  `if (typeof window === "undefined") return;`. `setInterval` — только
  внутри `GameLoop` и не в конструкторе.
- Имена событий стабильны. Новое событие должно иметь реального подписчика
  (bridge или сервис логики).
- UI не читает состояние логики напрямую: только store и публичные команды.
- Bridge и запуск цикла инициализирует composition root (`page.tsx` или
  провайдер), а не UI-команда.

## Данные и типы

- `src/data/*.json` — статический контент, только чтение. Runtime-экземпляры
  создаёт логика при инициализации.
- `XxxData` — wire-формат (числа строками), `IXxx` — контракт класса
  (числа `Decimal`). Класс `implements IXxx`.
- `XxxData` переносится в `src/shared/types/`, только если используется
  больше чем одним слоем. `IXxx` всегда остаётся в файле класса.
- Два независимых формата сериализации:
  - `serializeForStore()` — форматированные строки для UI (`toFixed`);
  - `serializeForSave()` / `deserializeForSave()` — lossless (`toString`).
  Смешивать форматы нельзя: сохранение потеряет точность Decimal, store
  получит нечитаемые числа.
- Всё сохраняемое реализует `Saveable`
  (`src/logic/services/GameSave/Isaveable.ts`) и регистрируется в `SaveManager`.

## Код

- TypeScript strict, без `any` в новом коде.
- Комментарии — по-русски, там где логика не очевидна.
- Классы и файлы классов — PascalCase, имя файла = имя класса.
- Один файл = один класс + его интерфейсы.
- События: `"tick"`, `"speed:changed"`, `"economy:changed"`;
  стиль `noun:past_tense` или глагол для команд.
- Иерархия: `System` координирует модуль, `Manager` управляет коллекцией
  однотипных сущностей, класс без суффикса описывает одну сущность.
- Внутри одной системы менеджеры могут вызывать публичные методы друг друга
  напрямую, если это следует из логики (например `BuildingManager` → `ResourceManager`).
  Между системами — только EventBus.
- Ресурсы меняет только `ResourceManager`. Другие менеджеры передают
  `ResourceRequest[]` и вызывают `processRequests` / `applyRequests`,
  а не мутируют `Resource` и не используют `getResource`/`getAllResources`.
- Запросы на одну фазу собираются одним батчем: приоритеты и дефицит
  распределяются по общему массиву, а не по каждому зданию отдельно.
- Внутри подсистемы прямой вызов допустим по цепочке «менеджер → своя
  сущность». Сущность не вызывает менеджер и не работает с сущностями
  чужого менеджера.
- Класс не знает о «родителе»; элемент не вызывает методы менеджера напрямую.
- Эталонные файлы структуры: `Resource.ts`, `ResourceManager.ts`,
  `EconomySystem.ts`. Архитектурные инварианты выше приоритетнее их текущего кода.

## Тесты

- Раннер — Vitest. Unit-тесты лежат рядом с кодом:
  `src/logic/**/*.test.ts`, позже `src/integration/**` и
  `src/components/**/*.test.tsx`.
- Общая инфраструктура — `src/test/` (setup, helpers, fixtures, mocks).
  Это не папка для самих тестов.
- Ожидаемое поведение берётся из `docs/game-design_v1.md`, а не из текущей
  реализации. Если тест и код расходятся — сначала выясни, что неверно.
- Известный баг оформляется `test.fails` с комментарием и ссылкой на
  `docs/status.md`; после исправления тест становится обычным.
- Уровни, стек и порядок покрытия — в
  [`plans/testing-strategy.md`](plans/testing-strategy.md).

## Workflow

- Перед изменением прочитай релевантные документы и определи слой, которого
  касается задача.
- Одна задача = одно изменение. Не смешивай рефакторинг, фичу и тесты.
- Не меняй поведение и соседний код за пределами задачи.
- Проверки: `npm run lint`, `npm run build`, `npx tsc --noEmit`,
  `npm run test`.
- Если не уверен — спроси. Заглушки и TODO вместо реализации не создавай.

## Commands

- `npm run dev` — dev-сервер, основной способ ручной проверки
- `npm run build` — production build
- `npm run lint` — ESLint
- `npm run test` — Vitest, один прогон
- `npm run test:watch` — Vitest в watch-режиме
- `npm run test:coverage` — Vitest с отчётом покрытия

## Don't

- Не добавлять новые зависимости без запроса.
- Не переименовывать файлы, классы и события «для красоты».
- Не менять `src/data/*.json`.
- Не переписывать `EventBus` — он стабилен.
- Не трогать `next.config.ts`, `tsconfig.json`, `package.json` без запроса.
- Не генерировать заглушки/TODO вместо реализации.
- Не «улучшать» архитектуру за пределами текущей задачи.
